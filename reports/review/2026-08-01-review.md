# Belay Review — 2026-08-01

Scope: redteam

This is the first report written to `reports/review/`, so its findings begin at
F-001. **They are a separate series from the `Finding N` entries in
`docs/HANDOFF.md`**, which that document states are "positions in this table,
not durable identifiers" (`docs/HANDOFF.md:1996`). F-001 here is not HANDOFF's

## Verdict

The most dangerous thing found is that `ArtifactFactory.create()` will mint a
signed, valid STRATEGY artifact already standing at `PRODUCTION` or
`MICRO_CAPITAL` — the review path that moves a strategy between stages is
carefully guarded and the path that *creates* one at any stage is not, so the
whole promotion pipeline is bypassable by declaring the destination at birth.
Nothing blocks the current ROADMAP stage: Stage 3 (Backtester) is unstarted and
none of these findings sit in its way — but F-001 and F-003 both become
load-bearing the moment Stage 3 produces a number a promotion review reads.

## Findings

### F-001 — A strategy can be created already standing at PRODUCTION — **Critical**

**Claim.** The lifecycle guard is on movement, not on birth. Nothing prevents a
STRATEGY artifact from being signed into existence at a capital stage it never
climbed to.

**Evidence.** `framework/artifacts/factory.py:14-19` — `create()` takes
`**kwargs` and passes `strategy_stage` through untouched.
`framework/artifacts/validator.py:145-169` — `_validate_lifecycle` checks three
things about `strategy_stage`: that it is a `StrategyLifecycle`, that STRATEGY
artifacts have one, and that non-STRATEGY artifacts do not. It never looks at
*which* stage. Run against the repository as committed:

```
ArtifactFactory().create(identifier="STRAT-0001", title="Newborn",
                         artifact_type=ArtifactType.STRATEGY,
                         strategy_stage=StrategyLifecycle.MICRO_CAPITAL)
→ ACCEPTED — artifact created at stage: StrategyLifecycle.MICRO_CAPITAL
  ArtifactValidator().validate(art) → True

... strategy_stage=StrategyLifecycle.PRODUCTION
→ ACCEPTED — artifact created at stage: StrategyLifecycle.PRODUCTION
```

The contrast is the finding. The same probe through the movement path is
refused, twice, by the transition table at `framework/artifacts/review.py:282`:

```
IDEA -> Micro Capital : refused — Invalid lifecycle transition
IDEA -> Validation    : refused — Invalid lifecycle transition
```

And `factory.py:20-39` already applies exactly the missing pattern to two other
fields — `integrity_hash` and `evidence_level` are refused from callers because
"a caller-provided grade is an assertion nobody checked, in the one place the
constitution is most explicit that assertions do not count". `strategy_stage` is
that same kind of field and is not in the list.

**Breach.** `constitution/Paper_First_Capital_Doctrine.md:5-7` — "Every strategy
begins with zero capital. No exceptions." Also
`constitution/Immutable_Laws.md:23-25` (Law III, capital must be earned) and
`constitution/Immutable_Laws.md:39` (Law V, no department may bypass
validation).

**Failure.** A strategy is registered at `MICRO_CAPITAL` because whoever created
the artifact knew the stage it "should" be at, or because a fixture, an import
script, or a Stage 5 service constructs strategies from a config file that
carries a stage field. It has no VALIDATION artifact and no PAPER_TRADING
history behind it, because it never occupied those stages. Every downstream
check — `Capital_Authority.md`'s six inputs, the promotion review, the demotion
floor — reads the stage as established fact and sizes real money against it. The
audit trail that would expose this is the sequence of REVIEW artifacts, and
there are none to be missing, because no review ever happened.

**Proposal.** Refuse a non-`IDEA` birth stage in `ArtifactFactory.create()`, in
the same shape as the `integrity_hash` and `evidence_level` refusals directly
above it: if `artifact_type is STRATEGY` and `strategy_stage` is neither absent
nor `IDEA`, raise. Every stage after IDEA is then reachable only through
`validate_transition`. If a legitimate need exists to reconstruct an artifact at
a later stage — deserialization is the obvious one — that path should be named
explicitly and take the review chain that justifies the stage, rather than being
the default behaviour of the sanctioned creation path.

### F-002 — No fetch record is ever written to disk, and `.gitignore` rests on the belief that they are — **High**

**Claim.** `fetch_and_record` builds the signed record that ADR-013 rule 3
requires and returns it in memory. Nothing in Belay persists it. The record of
every fetch that has ever run is gone.

**Evidence.** `framework/data/fetch_record.py:203` returns `Fetch(...)` and no
caller stores `record`. `git ls-files | grep -i "\.ya?ml"` returns nothing — not
one artifact of any type is committed. `ArtifactRepository` is instantiated
nowhere outside its own module (`framework/artifacts/repository.py:27`) and the
test suite. The only production caller of `fetch_and_record` is
`scripts/verify_clone.py:67`, which writes its store into
`tempfile.mkdtemp(...)` at `scripts/verify_clone.py:61` and deletes it at
`scripts/verify_clone.py:177` (`shutil.rmtree(root, ignore_errors=True)`); the
returned `record` is read for two assertions and dropped.

The one series Belay actually holds —
`data/market/dolthub-stocks/AAPL/0001-a7dbcaf3fb6aba2d.bin`, 28 bars over
2024-01-02 to 2024-02-09 — has no record anywhere in the repository.

`.gitignore:46-49` is the claim this falsifies, verbatim: "Nothing is lost by
this. Rule 3 already covers the integrity requirement: the fetch record artifact
carries the content hash, so the record of what was obtained is signed and
permanent whether or not the bytes are under version control." The record is
neither signed into anything durable nor permanent. `framework/data/store.py:22`
makes the same argument from the other side.

**Breach.** `constitution/Governance.md:27` — "Institutional memory is
mandatory." `framework/data/fetch_record.py:14-21` states that the fetch record
is precisely what Law VII (`constitution/Immutable_Laws.md:51`) requires Belay
to retain, and it is retained nowhere.

**Not rated Critical, and the reason matters.** Law VII forbids knowledge being
*intentionally discarded*. This is a gap rather than a decision — no persistence
layer was ever wired up — so the Law's own wording does not cleanly reach it.
The Governance breach is unambiguous and that is what the rating rests on.

**Failure.** A metric is computed on the AAPL series and enters a promotion
review. Someone later asks what data produced it. The bytes are gitignored, so
they exist on exactly one machine; if that machine is reimaged, or the store is
cleared, or the fetch is simply re-run against a vendor that has since restated
history, there is no signed hash to compare against and no record that the
original fetch happened at all. Rule 3's "re-fetch, hash, compare" — the entire
reproducibility argument for not committing the data — cannot be executed,
because one side of the comparison was never stored. The irreproducibility is
silent, which is the exact failure `store.py:11` says the design exists to
prevent.

**Proposal.** Give `fetch_and_record` a repository to write to, or add a thin
`scripts/fetch.py` that saves the returned record through
`ArtifactRepository.save()` into a tracked directory, and point `.gitignore`'s
justification at that directory by name. Until a record for the AAPL series
exists, `.gitignore:46-49` should say what is actually true.

### F-003 — A statistical review cannot carry the survivorship disclosure — **High**

**Claim.** `significance_artifact` takes a source *name* rather than a source,
and builds its `Disclosure` inline. A Validation Report computed on survivor-only
data therefore carries no survivorship caveat at all, unless the caller
volunteers one.

**Evidence.** `framework/metrics/statistics.py:307-318` — the signature takes
`data_source: str` and `sample_period: SamplePeriod`, not a `MarketDataSource`.
`framework/metrics/statistics.py:359-364` constructs the `Disclosure` with
`known_limitations=limitations`, where `limitations` is `KNOWN_LIMITATIONS` (the
t-test caveat) plus an optional `additional_limitations`. Nothing consults the
source. Run against the repository as committed:

```
DoltHubStocksSource().survivorship.is_clean → False
significance_artifact(..., data_source=DoltHubStocksSource().name, ...)
known_limitations mentions 'urvivor'? → False
```

The artifact carries the real source's identity and none of its bias.

`framework/data/fetch_record.py:227-263` — `disclosure_from()` exists precisely
to prevent this, and its docstring at `:250-253` states the rule it enforces:
"There is no `survivorship` parameter and no `source_name` parameter ... taking
the name rather than the source let a fabricated disclosure be paired with a
real source's identity." That is a description of `significance_artifact`'s
current signature. `disclosure_from` has **zero non-test callers**
(`grep -rn "disclosure_from" --include=*.py .` returns only its definition and
three test files), and cannot be used here at all, because
`significance_artifact` accepts no `Disclosure`.

**Breach.** `constitution/Evidence_Standards.md:45` — "Every conclusion must
reference supporting evidence." A significance verdict is the strongest
conclusion Belay draws, and this one omits the single property that most
distorts it. `docs/ROADMAP.md:208-213` records the owner ruling that the
survivorship fact and its direction are "a fixed module constant on every
artifact derived from that source, not a caller-supplied string"; on this path
it is neither.

**Failure.** A rule is backtested on free DoltHub equities. Its returns go to
`significance_artifact`, which reports p = 0.01 and `significant=True` in a
signed `Validation Report`. The report's `known_limitations` warns about
autocorrelation and multiple testing and says nothing about survivorship. The
promotion review reads it, sees a disclosed and apparently complete set of
caveats, and moves the strategy to `Validation`. The bias that inflated the
return and deflated the drawdown at the same time
(`framework/data/survivorship.py:71-79`) never entered the record, and the one
mechanism designed to force it there was structurally unreachable.

**Proposal.** Add a required `source: MarketDataSource` parameter to
`significance_artifact` and derive both `data_source` and the survivorship half
of `known_limitations` from it, keeping ADR-012 rule 7's fixed strings appended
rather than replaced — the same append-never-substitute shape
`disclosure_from` already uses at `fetch_record.py:254-256`. `cagr_artifact` and
the other `metric_artifact` callers should be checked for the same gap; they
accept a `Disclosure` and so *can* be fed by `disclosure_from`, but nothing
requires it.

### F-004 — `sample_adequate` is arithmetically identical to `significant` — **Medium**

**Claim.** ADR-012 rule 8 exists to separate "not significant" from "not enough
data to tell". The boolean that reports the second is the same boolean as the
first, so the distinction the rule was written for is not implemented by it.

**Evidence.** `framework/metrics/statistics.py` — `significance()` sets
`sample_adequate=len(returns) >= needed`, where `needed` is the smallest n
satisfying `effect * sqrt(n) >= t_critical_value(alpha, n-1)`
(`minimum_observations_for_significance`, the `clears()` closure). At the actual
n, `effect * sqrt(n)` *is* the t-statistic, so `clears(n)` is the significance
test itself; `clears` is monotone in n, so `n >= needed` ⟺ `clears(n)` ⟺
`significant`. Run against the repository as committed, 60 random series
(n between 5 and 60, gaussian returns, alpha 0.05):

```
trials: 60  mismatches: 0
distinct (significant, sample_adequate) pairs seen: {(True, True), (False, False)}
```

`tests/metrics/test_significance.py:226-239` asserts only the one-way
implication and its docstring concedes the mechanism — "Significance at n *is*
the condition that n meets the requirement" — while claiming "the informative
case is the negative one". The negative case of the boolean is equally
redundant. The *number*, `minimum_observations`, is genuinely informative; the
boolean beside it is not.

**Breach.** `constitution/Operational_Constraints.md:19` — "Belay shall
communicate uncertainty explicitly." A field that cannot disagree with its
neighbour communicates nothing and reads as if it can.

**Failure.** A promotion review reads a `Validation Report` and sees
`significant=True` and `sample_adequate=True` in the signed parameters. It
records that two independent checks passed. One check passed, twice. When a
sample is genuinely thin the reviewer sees `significant=False` and
`sample_adequate=False` and reads it as "the strategy failed", which is exactly
the conflation `minimum_observations_for_significance`'s docstring says rule 8
refuses.

**Proposal.** Either drop the boolean and report `minimum_observations` alone —
it carries all the information — or define adequacy against something
independent of the observed effect, such as a minimum observation count or a
minimum span. Whichever is chosen, the test at
`tests/metrics/test_significance.py:226` should assert the relationship that
actually holds (equivalence) rather than the weaker implication, so the
redundancy is visible in the suite instead of argued away in a docstring.

### F-005 — `DailyBarSeries` accepts duplicate dates — **Medium**

**Claim.** The ordering guard passes duplicates, so the same trading day can
appear any number of times in a series that presents itself as validated.

**Evidence.** `framework/data/contract.py:99-105` — the check is
`if dates != sorted(dates)`. `[d1, d1, d1, d2]` is sorted, so it passes. Run
against the repository as committed:

```
DailyBarSeries(symbol="AAPL", bars=(bar, bar, bar, later))
→ accepted: 4 bars; period: 2020-01-02 .. 2020-01-03
```

`framework/data/dolthub.py:365` sorts parsed bars but never de-duplicates, and
`dolthub.py:295` sorts the concatenated chunks without de-duplicating either.

**Breach.** `constitution/Operational_Constraints.md:5` — "Belay shall maintain
accurate records." A series asserting four observations over two trading days is
not one.

**Failure.** *Prediction, and it runs in the flattering direction.* A duplicated
bar produces a `P_t / P_(t-1) - 1` of exactly 0.0 in `period_returns`
(`framework/metrics/returns.py:61-63`). Fabricated zero returns pull the
standard deviation down while barely moving the mean, so the standard error
falls, the t-statistic rises, and `significant` flips true on a record that did
not earn it. The fetch record's `observations` count
(`framework/data/fetch_record.py:97`) and every artifact's `provenance` string
inherit the inflated count. Nothing anywhere would report the duplication.

*Fact, and it bounds the finding:* the one series landed today has no
duplicates, so this has not yet produced a wrong number. The route in is a
vendor emitting a repeated row, or any future adapter that concatenates
overlapping windows — the current chunker does not overlap
(`dolthub.py:191-199`), which is why this is a prediction rather than an
observation.

**Proposal.** Change the guard in `DailyBarSeries.__post_init__` to reject
non-*strictly* increasing dates: `if any(b <= a for a, b in zip(dates, dates[1:]))`.
One line, and it subsumes the ordering check it replaces.

### F-006 — A series with a hole in it discloses full coverage — **Medium**

**Claim.** `sample_period` is derived from the first and last bar, so a series
missing an arbitrary amount of its middle claims the whole span. Nothing
compares the observation count against the window it claims to cover.

**Evidence.** `framework/data/contract.py:107-120` — `period()` returns
`SamplePeriod(start=self.bars[0].date, end=self.bars[-1].date)`.
`framework/data/fetch_record.py:261` feeds that straight into
`Disclosure.sample_period`. Run against the repository as committed:

```
DailyBarSeries with exactly 2 bars: 2015-01-02 and 2017-12-29
disclosure_from(...).sample_period → 2015-01-02 .. 2017-12-29
```

Two observations, disclosed as three years.

The gap has a live route in. `framework/data/dolthub.py:360` —
`body.get("rows", ())` — makes a month that returns zero rows a *successful*
chunk, not an error. The comment at `framework/data/dolthub.py:286-288` promises
"the whole fetch fails rather than returning a series with a hole in it", but
that promise is inside an `except SourceUnavailable` block: it covers a chunk
that *failed*, not a chunk that succeeded and was empty. A vendor gap therefore
passes through silently.

**Breach.** `constitution/Evidence_Standards.md:45`, and
`framework/data/fetch_record.py:243-245`, which states the standard this
violates: "A disclosure stating the requested window would claim coverage the
data does not have." The disclosure states the *covered* window and still claims
coverage the data does not have, because coverage is not the same as span.

**Failure.** *Prediction.* A backfill runs over 2015–2024 for a symbol whose
vendor rows have an eighteen-month hole. Every chunk returns Success. The fetch
record says N bars covering 2015-01-02 to 2024-12-31 and both numbers are
individually true. A CAGR is computed with `periods_per_year=252` — the caller
supplies it, and nothing connects it to the dates — so the missing eighteen
months are annualized away as though they never existed, and the sample period
on the signed artifact tells a reviewer the strategy was tested across a decade
including a drawdown regime it never saw.

*Fact:* the one series landed today is dense — 28 bars, no calendar gap over 4
days — so this has not yet produced a wrong number.

**Proposal.** Record the observation count *and* the span together in the
disclosure, and have `DailyBarSeries` expose a density figure so the two can be
compared: a `SamplePeriod` of three years carrying two observations should be
visibly wrong on the face of the artifact. The stronger version is a
`max_gap_days` field on the fetch record, so a hole is a stated property rather
than something a reader must reconstruct.

## Not found

Looked for, and genuinely not found:

- **A path to a capital stage through the review machinery (D1).** The transition
  table refuses stage-skipping in both directions tested; `IDEA -> Micro Capital`
  and `IDEA -> Validation` both raise at `framework/artifacts/review.py:282`.
  `_check_outcome_matches_movement` handles `RETIRED` before taking any ladder
  index, so the index-8 trap ADR-004 warned about is closed. The back door is at
  creation (F-001), not here.
- **A way to suppress the survivorship disclosure on the fetch path (A1, code
  half).** The two links hold: the constructor refuses a source with no
  disclosure (`framework/data/contract.py:201-211`), the property is read-only,
  and `_survivorship_of` (`framework/data/fetch_record.py:206-224`) re-checks at
  the point the answer is signed, catching a subclass that skips
  `super().__init__()`. Confirmed by reading, not by running an override.
- **A delisted name inside the landed sample (A1, dataset half).** There is
  none — but that is not a defect, it is the disclosed property. The only data
  landed is AAPL, a survivor, and the source states
  `delisted_prices=SURVIVORS_ONLY` with a basis established by query
  (`framework/data/dolthub.py:138-170`). The checklist's question — can you name
  one delisted company present in the sample — has the answer "no, and the
  source says so in every artifact it touches". The dataset half of A1 will only
  become a finding when a source claims better than it delivers.
- **Duplicate or gapped bars in the data that has actually landed (A5).** Parsed
  all 28 bars of the single stored payload: 0 duplicates, 0 gaps over 4 calendar
  days, span 2024-01-02 to 2024-02-09, both chunks `query_execution_status:
  Success`. F-005 and F-006 are about what the types permit, not about this file.
- **An undisclosed multiple-testing problem (B1).** `KNOWN_LIMITATIONS` at
  `framework/metrics/statistics.py:57-66` states plainly that no correction is
  applied, that Belay does not record how many strategies were tried, and that
  the p-value is therefore optimistic. It is fixed rather than caller-supplied.
  The gap — that nothing *counts* the discarded attempts — is real but disclosed,
  and the checklist's own standard is that a disclosed limitation is not a
  finding.
- **Defaulted metric conventions (B4).** `periods_per_year`
  (`framework/metrics/returns.py:66`), `alpha` and `null_return`
  (`framework/metrics/statistics.py:249-254`) all have no defaults and are
  recorded in artifact `content`, so two Sharpes cannot silently differ in
  convention.
